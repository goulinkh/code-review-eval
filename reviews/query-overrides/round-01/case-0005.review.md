**Finding: an overridden key is moved to the end of the query, which changes which singleton value the endpoint reads.**

Location: `src/request_url.py`, head lines 15-16 (base has no equivalent; the lines are new in this change).

The loop drops every existing occurrence of an overridden key and then appends `(key, value)` at the end of the field list. The endpoint reads the first occurrence of singleton fields such as `sort`, so the key's position matters.

Triggering input:
- `request_url("https://h/c?sort=name&page=2&sort=date", {"sort": "price"})` returns `?page=2&sort=price`. That is valid for this case, because only one `sort` remains.
- Reordering is still a problem when the query contains other keys. Consider `?sort=name&q=a&q=b` with the overrides `{"q": "x"}`. The result is `sort=name&q=x`, which is fine. Now override `sort` with `{"sort": "price", "q": "x"}` instead. The result is `q=x&sort=price`, so `sort` is no longer first among fields.

This reordering is not harmful when each key occurs once. It does become a defect if a consumer relies on a stable parameter order. The description only says the endpoint reads the first occurrence of a key, so this is a weak, order-sensitivity-only concern. I would not block the change on it.
